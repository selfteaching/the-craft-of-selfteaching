# چطور ثابت کنید که واقعاً این کتاب را خوانده‌اید؟

> **یادداشت مترجم — توضیح تکمیلی:** نویسندهٔ اثر اصلی Li Xiaolai است. این بخش با متن اصلی مقابله و بازبینی شده، اما نهایی نیست. راهنمای GitHub و JupyterLab، تصاویر و برنامه‌های آیندهٔ نویسنده مربوط به زمان نگارش‌اند؛ رابط و روند امروزی ابزارها در این ترجمه آزمایش نشده است. دستورها عیناً حفظ شده‌اند و اجرا نشده‌اند. ترجمه فقط برای مطالعهٔ شخصی و محلی است؛ دستورهای مربوط به انتشار، از جمله `git push` و ارسال Pull request، مجوز انتشار ترجمه نیستند. تا دریافت اجازهٔ لازم، ترجمه را به مخزن عمومی نفرستید.

## کتاب‌هایی که می‌خریم و نمی‌خوانیم: 積ん読

در زبان ژاپنی واژهٔ جالبی وجود دارد: **積ん読**، یا [tsundoku](https://en.wikipedia.org/wiki/Tsundoku):

> کتاب‌هایی که می‌خریم و گوشه‌ای روی هم می‌گذاریم، اما هنوز نخوانده‌ایم؛ حتی گاهی سرانجام کلاً از خواندنشان منصرف می‌شویم…

اگر کمی فکر کنیم، همهٔ ما تعداد زیادی از این کتاب‌ها داریم. حتی در کودکی هم بخش قابل‌توجهی از کتاب‌های درسی که به خانه می‌آوردیم همین سرنوشت را داشتند. آن روزها پدر و مادرمان پول کتاب‌ها را می‌دادند و خودمان هم می‌دانستیم وقتی آن‌ها را با دقت نمی‌خوانیم، یا اصلاً نمی‌خوانیم، داریم تنبلی می‌کنیم. بعدتر دیگر آگاهانه «مرتکب جرم» می‌شدیم! برای مثال، خیلی‌ها در کتاب‌های واژگان انگلیسی که خریده‌اند، حتی به فهرست دوم هم نرسیده‌اند. برای همین قبلاً به شوخی می‌گفتم همهٔ دانش‌آموزان چینی دست‌کم یک واژهٔ انگلیسی را می‌شناسند: *abandon*، مگر نه؟ این واژه شاهد انکارناپذیر عزم خیلی‌ها برای «از نو شروع کردن» و سپس «بی‌خیال شدن» است.

> **یادداشت مترجم — توضیح تکمیلی:** abandon یعنی «رها کردن». شوخی نویسنده به کتاب‌های واژگانی اشاره دارد که با ترتیب الفبایی تنظیم شده‌اند و این واژه در ابتدای آن‌ها قرار می‌گیرد: خواننده همان اول کار به واژهٔ «رها کردن» می‌رسد و بعد خود کتاب را رها می‌کند.

پیش از پیدایش کتاب الکترونیکی، کتاب‌های چاپی دست‌کم تا حدی نقش «وسیلهٔ تزئینی» را داشتند. اما حالا چه کسی می‌داند چند کتاب پولی در دستگاه شما هست؟ این‌همه جمع کرده‌اید، اما جایی هم نیست که آن‌ها را به رخ بکشید؛ قرار است به چه کسی نشانشان بدهید؟ گفته می‌شود آمار داخلی Kindle به‌روشنی «نرخ باز شدن» کتاب‌ها را نشان می‌دهد؛ رقمی حدود یک‌چهارم تا یک‌سوم. یعنی تقریباً دوسوم تا سه‌چهارم کتاب‌های الکترونیکی، پس از خرید و دانلود، حتی یک بار هم باز نشده‌اند.

> **یادداشت مترجم — نیازمند بررسی:** نویسنده برای آمار Kindle در این بخش منبعی ارائه نکرده است. این ارقام به‌عنوان ادعای متن اصلی نقل شده‌اند، نه آمار تأییدشده یا به‌روز.

با این حساب، وقتی پول کتاب را می‌دهیم و آن را نمی‌خوانیم، فقط یک نفر را می‌توانیم فریب بدهیم: خودمان را. برخلاف تصور پیشین بعضی روان‌شناسان، من فکر می‌کنم آدم‌ها معمولاً خودشان را فریب نمی‌دهند؛ دست‌کم «عمداً خود را فریب دادن» برایشان آسان نیست. به همین دلیل، به نظرم «ایجاد رضایتی کاذب در خود» بهترین توضیح برای پدیدهٔ «خریدن و بعد به‌هیچ‌وجه نخواندن» نیست.

توضیحی ساده‌تر و نزدیک‌تر به واقعیت این است:

> آن هفتاد یا هشتاد درصد، در واقع می‌خواهند روزنهٔ امیدی برای خودشان نگه دارند…

«وقتی وقت پیدا کنم، حتماً می‌خوانمش.» بله، همین.

خنده‌دار است، اما یکی از هدف‌های مشترک همهٔ ما این است:

> جزو اقلیت بیست درصدِ برتر باشیم…

درحالی‌که راه جلو افتادن از هفتاد یا هشتاد درصدِ دیگر واقعاً بسیار ساده است:

> کافی است کتاب‌هایی را که می‌خرید واقعاً و با دقت بخوانید.

بیش از حد ساده به نظر می‌رسد، نه؟ اما… می‌دانم همین حالا چه فکر نه‌چندان افتخارآمیزی از سرتان گذشت:

> خب، پس کمتر کتاب بخرم، یا اصلاً نخرم؛ مشکل حل نمی‌شود؟

خودتان هم می‌دانید این استدلال بی‌معناست، ولی باز نمی‌توانید از این زرنگی کوچک احساس رضایت نکنید. راستش خوشبختانه شما هم هستید؛ وگرنه ما چطور می‌توانستیم خودمان را به جمع آن بیست درصد برسانیم؟

## PoW

در Bitcoin، که نخستین کاربرد blockchain در جهان است که عملی بودنش واقعاً اثبات شده، مفهوم بسیار مهمی وجود دارد: **Proof of Work**، یا به‌اختصار **PoW**. اگر کاری انجام داده‌اید، انجام داده‌اید؛ اگر انجام نداده‌اید، نداده‌اید. کاری که کرده‌اید قابل اثبات است…

> **یادداشت مترجم — توضیح تکمیلی:** blockchain روشی برای ثبت زنجیره‌ای داده‌هاست. Proof of Work در Bitcoin سازوکاری فنی برای اثبات انجام کار محاسباتی است؛ نویسنده در اینجا فقط از ایدهٔ «داشتن شاهدی برای کار انجام‌شده» الهام می‌گیرد. ثبت مطالعه در Git همان سازوکار فنی Bitcoin نیست.

با الهام از این ایده، روشی طراحی کرده‌ام تا بتوانید ثابت کنید که این کتاب را واقعاً خوانده‌اید و به پایان رسانده‌اید. هم به خودتان و هم به دیگران می‌توانید نشان دهید قبلاً چه کاری انجام داده‌اید. جالب نیست؟

برای این کار از وب‌سایت [github.com](https://github.com) و ابزار کنترل نسخهٔ **Git** استفاده می‌کنیم.

> **یادداشت مترجم — توضیح تکمیلی:** Git تاریخچهٔ تغییرات فایل‌ها را نگه می‌دارد؛ GitHub وب‌سایتی برای میزبانی و همکاری روی مخزن‌های Git است. یک repository یا مخزن، فایل‌های پروژه و تاریخچهٔ آن‌ها را در بر می‌گیرد. این سابقه می‌تواند ردّی از تمرین‌های شما باشد، اما به‌تنهایی ثابت نمی‌کند که مطالب را فهمیده‌اید.

## مراحل کار

این مراحل را دنبال کنید:

> 1. در [github.com](https://github.com) حساب بسازید؛ درهرحال به یک حساب GitHub نیاز دارید.
> 2. با مرورگر به [https://github.com/selfteaching/the-craft-of-selfteaching](https://github.com/selfteaching/the-craft-of-selfteaching) بروید.
> 3. دکمهٔ «Fork» را در بالای سمت راست صفحه پیدا کنید و از مخزن در حساب خودتان یک Fork بسازید.
> 4. با دستور `git clone` یا ابزار [Desktop for GitHub](https://desktop.github.com/)، مخزن [the craft of selfteaching](https://github.com/selfteaching/the-craft-of-selfteaching) را که Fork کرده‌اید، روی رایانهٔ خود clone کنید.
> 5. مطابق [راهنمای نصب و تنظیم JupyterLab، به زبان اصلی چینی](../../markdown/T-appendix.jupyter-installation-and-setup.md)، JupyterLab را روی رایانهٔ خود راه‌اندازی کنید. اگر کتاب را در JupyterLab بخوانید، می‌توانید همهٔ کدهای آن را همان‌جا اجرا کنید و حتی مستقیم تغییرشان بدهید و با آن‌ها آزمایش کنید.
> 6. هنگام خواندن، کدهای متن را تغییر دهید و تمرین کنید. به این ترتیب فایل بخش‌هایی که خوانده‌اید تغییر می‌کند. پس از هر فصل، یا حتی در طول مطالعه، می‌توانید با دستور `git commit` تغییرات را در مخزنی که Fork کرده‌اید ثبت کنید. این همان شاهد کار شما هنگام خواندن است.
> 7. در مخزن پوشه‌ای به نام `my-notes` وجود دارد. می‌توانید یادداشت‌های یادگیری خود را آنجا قرار دهید.
> 8. پوشهٔ دیگری به نام `from-readers` برای جمع‌آوری بازخورد خوانندگان وجود دارد. بعدها می‌توانید نوشته‌ای با عنوان «مسیر خودآموزی من» تهیه کنید، آن را در این پوشه قرار دهید، یک branch جدا بسازید و Pull request بفرستید تا دیگر خوانندگان به آن رأی بدهند. اگر میزان موافقت به حد معینی برسد، نوشتهٔ شما در مخزن اصلی قرار می‌گیرد تا افراد بیشتری آن را ببینند و مانند شما به خودآموزی تشویق شوند…

> **یادداشت مترجم — توضیح تکمیلی:** Fork نسخه‌ای از مخزن در حساب GitHub شماست؛ clone یک نسخهٔ محلی از مخزن می‌سازد. commit یک نقطهٔ ثبت در تاریخچهٔ محلی است و خودش چیزی را به سرور نمی‌فرستد. branch مسیر جداگانه‌ای برای تغییرات در همان مخزن است. Pull request درخواست بررسی و ادغام تغییرات است. توضیح پذیرش نوشته‌های خوانندگان در بند آخر، طرح نویسنده در زمان نگارش است و وضعیت فعلی آن بررسی نشده است.

البته برای این کار باید چیز دیگری هم یاد بگیرید که دیر یا زود به آن نیاز پیدا می‌کنید: Git. به پیوست [آشنایی با Git، به زبان اصلی چینی](../../markdown/T-appendix.git-introduction.md) مراجعه کنید.

زمان همین است؛ نمی‌توانیم سرش کلاه بگذاریم. با ابزارهایی مانند Git هم به‌آسانی می‌توان نشان داد چه زمانی چه کاری انجام داده‌ایم. برای ما این واقعاً خبر بسیار خوبی است.

## کمک به بازبینی کتاب با Pull request

اگر هنگام خواندن، غلط تایپی، خطای کد یا حتی بیان بهتری برای مطلبی پیدا کردید، می‌توانید با Pull request به بهتر شدن کتاب کمک کنید. این هم نوعی شاهد کار است.

(۱) با مرورگر به https://github.com/selfteaching/the-craft-of-selfteaching بروید.

(۲) دکمهٔ «Fork» را در بالای سمت راست بزنید تا یک Fork از مخزن در حساب GitHub شما ساخته شود.

![ساخت Fork از مخزن در حساب شخصی](../../images/github-fork.png?raw=true)

(۳) یک branch تازه بسازید. می‌توانید نامی مانند `from-<your_username>` انتخاب کنید؛ مثال متن اصلی `by git.basic.tutorial` است. سپس برای ساخت branch روی Create Branch کلیک کنید.

> **یادداشت مترجم — نیازمند بررسی:** عبارت `by git.basic.tutorial` همان مثال متن اصلی است، اما به دلیل داشتن فاصله، نام معتبر branch در Git نیست. آن را عیناً به‌عنوان نام branch وارد نکنید؛ توضیح نام‌گذاری در متن اصلی با مثال آن سازگار نیست.

![انتخاب نام و ساخت branch تازه](../../images/github-new-branch.png?raw=true)

(۴) در branch تازه فایلی را تغییر دهید و سپس تغییر را ثبت کنید. پیش از ثبت، از نوشتن توضیح روشن دربارهٔ تغییر در بخش Comment صرف‌نظر نکنید.

![ثبت تغییر همراه با توضیح آن](../../images/github-commit.png?raw=true)

در تصویر نمونه، فایل README.md تغییر کرده است؛ اما آنچه شما ارسال می‌کنید باید واقعاً یک اصلاح لازم باشد.

همچنین **توجه کنید:** پیش از ساخت branch، باید Fork خود را به آخرین نسخه به‌روز کنید. روش این کار در بخش بعد، «همگام کردن Fork با مخزن اصلی در وب‌سایت GitHub»، آمده است.

(۵) در بالای صفحه زبانهٔ Pull request را انتخاب کنید:

![باز کردن بخش Pull request](../../images/github-pull-request.png?raw=true)

سپس دکمهٔ `Compare & pull request` را بزنید. اگر این دکمه را نمی‌بینید، روی پیوند مربوط به تغییر تازهٔ فایل در پایین صفحه کلیک کنید؛ مانند «Update README.md» در تصویر بالا، که عنوانی است که هنگام ثبت تغییر نوشته‌اید.

![مقایسهٔ تغییرات و باز کردن درخواست](../../images/github-open-pull-request.png?raw=true)

پس از بررسی درستی اطلاعات، روی `Create pull request` کلیک کنید.

![ساخت Pull request پس از بررسی اطلاعات](../../images/github-create-pull-request.png?raw=true)

(۶) سپس به کاربر GitHub با نام [@xiaolai](https://github.com/xiaolai)، یعنی من، صاحب مخزن the-craft-of-selfteaching، اطلاع داده می‌شود که کسی Pull request فرستاده است. من چنین صفحه‌ای می‌بینم:

![صفحهٔ بررسی درخواست برای نگه‌دارندهٔ مخزن](../../images/github-confirm-merge.png?raw=true)

وقتی تأیید کنم که تغییر این Pull request درست و پذیرفتنی است، دکمهٔ `Merge pull request` را می‌زنم. به این ترتیب، من و شما با هم یک اصلاح انجام داده‌ایم.

![نتیجهٔ ادغام Pull request](../../images/github-merged-pull-request.png?raw=true)

**توجه**

بهترین روش برای ارسال Pull request این است:

> - پیش از ارسال، branch با نام `master` در Fork خود را با آخرین نسخهٔ مخزن اصلی همگام کنید.
> - برای افزودن یا اصلاح مطالب، از `master` یک **branch تازه** بسازید.
> - تا جای ممکن، هر بار فقط یک تغییر کوچک بفرستید.
> - دلیل تغییر را کوتاه و روشن توضیح دهید.
> - صبورانه منتظر پاسخ بمانید.

اگر در آزمایش‌های محلی، Fork خود را به‌هم ریخته‌اید، نباید همان وضعیت را مبنای ارسال Pull request قرار دهید. روی نسخهٔ محلی خود هر آزمایشی دوست دارید انجام دهید؛ اما برای فرستادن تغییر به دیگری، باید دوباره آخرین نسخه را روی رایانه بگیرید و تغییرتان را بر پایهٔ آن انجام دهید.

![نتیجهٔ ادغام و تکمیل همگام‌سازی](../../images/sync-fork-7.png?raw=true)

البته گاهی ممکن است با مشکلی روبه‌رو شوید که نتوانید حلش کنید. در آن صورت یک راه آخر هم هست:

> Fork خود را حذف کنید و دوباره در صفحهٔ https://github.com/selfteaching/the-craft-of-selfteaching دکمهٔ `Fork` را بزنید…

> **یادداشت مترجم — توضیح تکمیلی:** حذف Fork پیشنهاد متن اصلی است، نه توصیه‌ای بی‌خطر برای همهٔ موقعیت‌ها. پیش از حذف، تغییرات و اطلاعاتی را که فقط در Fork خود دارید بررسی و پشتیبان‌گیری کنید؛ همگام‌سازی عادی لزوماً به حذف مخزن نیاز ندارد. مراحل و تصاویر بالا نیز مربوط به رابط زمان نگارش‌اند.

## ثبت مسیر یادگیری با GitHub

می‌توانید روی رایانهٔ خود یک branch بسازید؛ مثلاً با نام `study`:

```bash
git branch study
git checkout study
```

پس از این کار، هر تغییری که در پوشهٔ کاری محلی ایجاد کنید، می‌تواند در branch با نام `study` ثبت شود.

هر بار که در JupyterLab فایل‌های `ipynb` را مرور می‌کنید و با `^ + Enter` کد یک code cell را اجرا می‌کنید، تغییراتی در فایل ایجاد می‌شود. می‌توانید هر بخش فایل را هم به دلخواه تغییر دهید: یک code cell اضافه کنید و قطعه‌کدی را از ابتدا تا انتها خودتان تایپ کنید؛ کد یک cell را تغییر دهید و ببینید نتیجه چه فرقی می‌کند؛ یا هر markdown cell را اضافه و ویرایش کنید و از آن برای یادداشت‌برداری استفاده کنید…

> **یادداشت مترجم — توضیح تکمیلی:** cell یک بخش مستقل در Notebook است؛ code cell برای کد و markdown cell برای متن قالب‌بندی‌شده به کار می‌رود. نشانهٔ `^` در میان‌بر بالا به Ctrl اشاره دارد. اجرای cell ممکن است خروجی یا شمارندهٔ اجرای ثبت‌شده در فایل را تغییر دهد؛ برای باقی ماندن تغییرات روی دیسک باید فایل ذخیره شود. این دستورها در این ترجمه اجرا نشده‌اند.

خلاصه، وقتی فصلی را می‌خوانید و مانند توضیح بالا تغییراتی ایجاد می‌کنید، فایل `ipynb` آن تغییر می‌کند. سپس می‌توانید این دستورها را اجرا کنید:

```bash
git add .
git commit -am 'my study result'
git push
```

> **یادداشت مترجم — توضیح تکمیلی:** `git add .` تغییرات زیر مسیر فعلی را برای ثبت آماده می‌کند؛ پیش از آن بررسی کنید فایل خصوصی یا نامرتبطی در میانشان نباشد. `git commit` ثبت محلی است، اما `git push` تغییرات را به مخزن راه‌دور می‌فرستد و ممکن است بدون تنظیم مقصد branch تازه موفق نشود. دستورها عیناً از اصل آمده‌اند؛ برای مطالعهٔ محلی، اجرای `git push` لازم نیست و دربارهٔ ترجمهٔ حاضر تا دریافت اجازهٔ انتشار نباید آن را به مقصد عمومی اجرا کنید.

به این ترتیب، مسیر یادگیری شما در branch با نام `study` ثبت می‌شود.

اگر در این مسیر متوجه شدید خود کتاب به اصلاح نیاز دارد، باید به branch با نام `master` بروید و این دستورها را اجرا کنید:

```bash
git checkout master
git pull
```

بعد تغییر را انجام دهید و با روشی که در بخش پیش توضیح دادیم، Pull request بفرستید.

در آینده، زیر مجموعهٔ [https://github.com/selfteaching](https://github.com/selfteaching) مخزنی ویژه راه‌اندازی می‌کنم تا سوابق یادگیری این کتاب را در GitHub به‌طور خودکار بررسی کند. چنین سوابقی در کتاب‌های گذشته نمی‌توانست وجود داشته باشد، اما حالا ممکن شده است. به نظر من، شاید در آینده اهمیت این سابقه حتی از «مدرک تحصیلی» هم بیشتر شود.
